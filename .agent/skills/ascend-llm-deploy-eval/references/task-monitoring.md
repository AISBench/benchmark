# Agent 提交、监控与上报

本指引用于 Agent 实际提交的远端任务。监控是应用侧行为，五阶段脚本继续负责执行和产出证据；不新增远端调度服务、不更改 job_spec，不为用户手工操作强加监控要求。

## 提交与绑定

1. 先检查本任务是否已有运行实例及监控记录，复用有效监控，不重复启动。确认远端任务包和 preflight 已完成。
2. 实际提交前必须按下节输出三类可复制观察命令（单任务和整组均适用），随后提交，不要求用户先运行这些命令。优先使用 scripts/submit_job.py submit 固定提交入口。兼容手动流程可使用现场可用的脱离会话方式启动生成的 run.sh，例如 nohup 配合 setsid，并明确重定向 stdin/stdout/stderr。Agent 可在任务目录生成最小启动包装脚本，记录开始时间、退出码和结束时间；记录用临时文件加原子替换。包装脚本不承担重试、恢复或模型清理。不要依赖本地 SSH 工具会话存活。
3. 登记实际协调器 PID、进程启动标识及命令，重新连接核验进程属于该任务，并确认执行状态或日志已经产生。shell 返回启动 PID 不等于执行器启动成功；快速结束的任务应直接核验终态。没有退出记录也不等于仍在运行。
4. 发现当前应用的定时监控能力。优先在当前聊天创建 heartbeat，默认每30分钟，已有用户频率要求优先；使用应用工具，不自行写入应用内部配置或改用系统 cron。保存工具返回的监控 ID，再读回确认绑定和启用状态。创建成功后立即检查一次任务。
5. 简要告知任务编号、远端目录及自动监控是否已建立。无法创建或核验监控时明确说明“任务已启动，但自动通知未启用”，给出查询入口；不因此终止已启动任务，也不声称一定会回来。需要本机 SSH 的监控依赖本机、应用和连接环境可用。

在仓库外的本地任务目录保存 monitor-state.json：job_id、plan 摘要、协调端和任务目录、当前聊天 ID、监控 ID/状态、执行器身份、最近检查时间、连续连接失败次数、最近已通知事件摘要及最终通知时间。仅保存现场可获得的标识，不编造 ID，不存凭据。该文件是 Agent 运行记录，不加入 Schema、不参与服务指纹。必要时另存启动记录到远端任务目录。

## 整组任务

按 group-execution.md 提交的整组任务只绑定一个监控，覆盖所有子任务；自动推进由远端进程负责。提交前向用户提供可复制的 SSH 观察命令。monitor-state.json 额外记录 group_id、整组主节点/目录、各事件流字节偏移及已通知源事件ID。沿用上述频率，启动后立即核验；不承诺即时通知。

先读取 group-summary.json、group-interrupted.json 和 group-state.json，再按游标读取新增 events.jsonl；终态必须核验全部子任务结果和释放证据。前置任务 FAILED 但 cleanup_verified 且整组继续时不单独通知；UNKNOWN 持续、BLOCKED、协调器中断或整组终态按下表通知。监控不执行后继启动或恢复。应用不支持指定频率时报告实际配置，不悄悄退回高频。

## 每次检查

读取监控记录和冻结计划，核对 job_id/计划摘要。检查 summary.json、task-state.json、各 sub_tasks/<id>/result.json、对应节点的 validated.json/summary.json 以及 release-results.json；证据位置以 resolved-cluster.json 的登记为准。只在状态不明时进一步查看进程身份、阶段日志或节点释放记录。避免每次拉取完整日志。

| 观察结果 | Agent 行为 |
|---|---|
| 正常运行、启动加载、预算内重试 | 更新检查记录，保持安静；不因日志暂未更新判断挂死 |
| 单次 SSH 失败、状态文件正在写入或暂缺 | 标记本次无法核验，下一次重查，不判定任务失败 |
| 连续3次监控无法核验 | 通知一次“监控失联/状态未知”；与执行器的重试预算分开，继续静默检查，恢复或状态变化再通知 |
| 进程已退出，缺少终态或清理证据 | 报告执行中断/结果未确认，指出需检查的证据；不自动重跑或释放身份不明资源 |
| record_only 子任务失败，服务核验允许继续 | 保持安静，最终统一汇总，不上报 Agent 修复 |
| 任务级阻塞或任务失败，清理仍进行 | 通知任务异常及清理待定一次，继续观察最终清理结果 |
| 需要改变负载、部署参数、权限或处理未知资源 | 提出具体问题，等待用户决定；监控不得替代授权 |
| 终态证据完整 | 汇总结果与清理结论，完成最终通知后停止监控 |

监控只能读取远端执行证据和维护自身记录。不要把 run.sh 当状态查询命令，不调用 deploy/evaluate/finalize，不重启服务、不杀进程。若确需后续修复或释放，作为单独的 Agent 行动按已有授权和归属证据处理，避免与仍在工作的执行器并发操作。

完成判定必须覆盖计划中的每个 sub_task，以及所有登记节点的任务级释放策略。成功要求结果与所需清理均通过；FAILED、NOT_RUN、REVIEW_REQUIRED、缺失证据均不能包装为成功。允许的 keep_service 策略按该策略核验，不强制要求所有容器停止。进程退出码、SSH 返回码、单个成功 case 都不能替代完整结论。

## 通知与停止

最终消息包含任务结论、异常和未执行项、任务清理结果及产物位置。性能指标仅在用户询问时呈现。

按 job_id、事件类型及结果摘要去重，普通日志时间变化不构成新事件。通知后保存已发送摘要；重复唤醒先查看聊天中的已发报告与记录，避免重复。聊天发送和本地记录不是原子事务，不宣称严格“仅一次送达”；中断后先核对再补记或补报。

最终通知交付后停用对应监控，并读回核验已停止。停止失败则记录、明确告知，后续唤醒只重试停止，不重复报告。需要人工处理但任务仍未收尾时，不把首次异常通知当最终完成；继续静默观察，或在明确移交用户/用户要求停止时停用并说明未确认项。

## 当前聊天监控提示词模板

创建时填入实际 job_id、协调端、远端目录及本地 monitor-state.json 绝对路径，不能只依赖聊天记忆：

> 检查任务 <job_id>，协调端 <host>，任务目录 <run_dir>，监控记录 <local_monitor_state>。遵循 ascend-llm-deploy-eval 的 references/task-monitoring.md。读取冻结计划、各子任务结果和全部登记节点的释放证据；正常运行、预算内重试及允许继续的 record_only 子任务失败保持安静，只在终态或需要人工处理的状态变化时通知。SSH 断连记为无法核验，不等同任务失败；不得重新运行任务、修改参数或自动清理。核验完成后报告任务结论、重试/异常、清理结果及产物位置，记录通知摘要，停用本监控并核验。若最终报告已发，只核验停止，不重复发送。

创建监控不会自动验证其实际唤醒和通知投递。首次正式使用时检查第一次触发记录；没有实测前，只报告“已创建并核验配置”，不声称通知链路已验证。

## 提交前的三类观察命令

交互侧正式提交前必须分别说明“使用此命令查看整体进展”“使用此命令查看服务日志”“使用此命令监控测试日志”，并输出已替换真实主机、任务路径的命令，不能只给占位模板或内部脚本名。使用冻结包中确实存在的脚本。以下仅为编写示例：

```sh
# 整体进展（持续观察事件）
ssh -t user@host.example 'python3 /work/JOB/common/skill-snapshot/scripts/watch_events.py --run-dir /work/JOB'
# 服务日志（发现后续启动与重试产生的新文件）
ssh -t user@host.example 'python3 /work/JOB/common/skill-snapshot/scripts/watch_logs.py --run-dir /work/JOB --kind service'
# 测试日志（AISBench 原始打屏，等待尚未创建的文件）
ssh -t user@host.example 'python3 /work/JOB/common/skill-snapshot/scripts/watch_logs.py --run-dir /work/JOB --kind test'
```

日志观察器只读，Ctrl+C 仅关闭观察，不停止任务。初始无文件时继续等待；不能使用提交时展开的通配符 tail 作为唯一日志命令，以免漏掉后续 attempt。多节点时按 node-map 的真实主机和节点目录分别提供服务/测试命令；整组的整体进展指向 GROUP，日志命令按各子任务/节点列出，不假设远端日志在主节点可见。30分钟是应用侧检查频率，不改变执行器自身轮询周期。
