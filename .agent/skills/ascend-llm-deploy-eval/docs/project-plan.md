## 目标与范围

以 job_spec 完成有人值守阶段的信息收集、脚本参数提取、现场绑定和预检，随后自动推进已授权任务。五阶段职责不变；单个任务内部串行，整组按服务器资源和任务依赖安排独立任务并发。优先正常执行路径与有限重试，不提前扩展通用集群调度平台。

## 默认策略

- 正式请求数=并发×4，运行1轮，首次尝试之外最多额外重试3次；用户明确覆盖优先。
- case 前重置缓存并预热，目标比例和实测命中率分别核验。有效 READY 服务跳过重新部署和冒烟。
- on_failure=record_only：记录失败并核验服务，安全条件满足则继续；未知身份、客户端残留或释放失败阻塞相关工作。
- 每台机器每个任务尽量复用一个兼容容器，不兼容配置另用子编号；任务结束默认停止服务并删除本任务容器。
- 整组执行要求子任务 task_end=stop_container。测量失败但任务级释放核验通过允许后继运行；最终整组仍体现失败。
- 远端协调器30秒轮询不调用模型；Agent默认60分钟检查一次，24小时约24次，实际提交时核验监控是否建立。

## 下一步验收顺序

1. **新默认容器实测**：使用已授权的小负载检查完整挂载、通信配置、服务冒烟和任务清理，保留 Docker inspect 与释放证据。
2. **整组真实小负载**：两台独立服务器各执行单机任务，确认并行、事件及服务归属；两侧释放后自动启动一个受支持的双机1P1D任务。验证关闭SSH观察终端不影响推进。
3. **监控闭环**：创建一个当前聊天监控，核验实际触发、正常静默、异常去重、终态报告和停止监控。不能只用创建成功代替投递验证。
4. **正式性能矩阵**：先检查上下文容量和部署适配；通过当前任务首个case实测估计剩余耗时。新负载不能沿用短输入成功结论。
5. **完整Agent与强弱模型复现**：按用户确认轮数复现，记录执行时实际可用型号和选择依据，比较结果、轨迹、工具调用及人工介入。

每一步按用户已授权的任务范围执行，更新工程文档不自动启动实际性能测试。

## 尚未覆盖的能力

- 多 P/D 拓扑（包括3P1D）、同机分卡并发、job_spec 内 phase 并行屏障。
- 主机别名自动归一、进程/主机崩溃后自动恢复、复杂故障分类与调参。
- 精度评测、配置库与版本检索。
- 长上下文配置适配：例如512K输入+5K输出合计529408 tokens，超过528000的上下文配置时须先解决，不能静默缩减负载。

## 产物边界

仓库仅保留实现、测试、公开占位示例与设计/工程计划。各任务的实际主机、镜像解析值、权重位置、日志、报告及脚本快照保存到仓库外。远端证据保留在任务目录；自动流程的归档要求不强加给用户手动操作。
