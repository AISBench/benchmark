## 1. 首版目标与限制

首先完成一个确定性测试任务的 Skill 开发，形成首版本 Skill 和脚本，并完成确定场景下的性能测试闭环。

- 假设部署过程无异常，首版聚焦正常执行路径；异常处理和恢复机制暂不作为本轮开发重点。
- 模型权重、容器镜像、测试工具默认已准备完毕，不在首版实现下载、安装或准备流程。
- 优先完成性能测试，精度测试后续再扩展。
- 冒烟测试暂采用单条真实推理请求，具体请求及通过判据在手工验证时确定。
- 固定测试场景，先验证该场景可执行、可复现，再提炼可复用配置与 Reference。
- 首版本 Agent 执行模式为 `plan - test`，计划前多轮对话补齐必要信息，计划后由 Agent 根据脚本反馈持续驱动执行；具体交接字段留待轨迹验证。

上述假设是本轮范围约束，不代表异常处理、环境准备或生产验收已经完成。

## 2. 开发与验证顺序

### 第一步：手工验证确定场景

先手工完成推理服务拉起、单条推理请求冒烟测试和性能测试。记录实际使用的环境、命令、配置、输入、输出及耗时，形成能够交给 Agent 执行的任务基线。

### 第二步：编写首版 Skill 和脚本，交给 Agent 执行一次

根据手工验证的有效步骤编写首版 Skill 和脚本。由 Agent 按 `plan - test` 模式执行一次完整任务，保留执行轨迹、阶段输入输出和时延记录。

### 第三步：从执行轨迹提取完整流程并人工调整

Agent 执行完成后，以实际轨迹为依据提取流程，由人工审阅和调整，分别设计：

- 询问阶段的提示词：明确需要询问、确认和补全的信息。
- 阶段交接的结构化 JSON：明确任务参数、上下文和执行所需信息。
- 各执行阶段的脚本：将已经验证的确定性操作固化。
- 输出的结构化形式：明确执行结果、性能结果、产物与时延的表达。

此阶段先依据真实任务提炼契约，不提前将原方案的全部字段与机制作为首版实现要求。

### 第四步：强弱 Agent / Model 复现与稳定性验证

准备强、弱两类 Agent / Model 组合，尤其使用能力较弱的组合复现同一个测试任务。比较完成情况、执行轨迹、输出及耗时，确认任务的稳定性。具体组合、重复次数和稳定性判据在后续讨论中确定。

### 第五步：依据实际任务组织配置与 Reference

根据手工验证、Agent 执行、人工调整及复现测试中实际使用的配置，确定 Reference 的组织形式。区分固定流程、场景配置和验证证据，避免提前构建未经真实任务验证的通用配方体系。

## 3. 过程记录要求

从手工验证开始，到 Agent 首次执行、人工调整及强弱组合复现，均保留可追溯记录。

- 记录各阶段开始、结束和耗时，以及端到端耗时。
- 区分流程执行时延与性能测试工具输出的推理性能指标。
- 记录执行者或 Agent / Model 组合、任务输入、实际配置、命令或脚本、输出和产物位置。
- 保留 Agent 执行轨迹与人工调整内容，用于流程提取和复现比较。

字段名称、时间口径和结构化输出 Schema 在后续设计时确定。

## 4. 当前代码状态

当前仓库仅包含目录框架、五个脚本入口、结构化阻止返回及独立复制执行测试。任务 Schema 尚为拒绝所有输入的占位定义；实际部署、测评、生产编排和资源清理尚未实现。

保留现有五脚本职责划分：plan_run 校验并生成计划，preflight 检查环境与资源，deploy 拉起服务并完成单请求冒烟，evaluate 执行性能测试，finalize 汇总归档并按约定清理。原方案 AC-01 至 AC-18 的完整生产验收仍未完成。

## 5. Agent 与脚本的职责共识

计划前由 Agent 多轮询问、查询环境、复用已有信息；信息齐备后再调用 plan_run 形成计划。脚本折叠各阶段内的操作，以减少工具调用和会话轮次，不替代模型判断。Agent 读取各脚本的结构化结果、耗时和异常证据，决定下一步；关键计划变更记录原因，超出确认范围时再询问用户。

正常路径按五脚本顺序推进，复杂异常交由 Agent 诊断。正常完成或中止均应进入 finalize，保留幂等与任务资源归属要求；Agent 调用不能保证语言级 finally 的执行语义，进程中断兜底后续设计。首版假设正常部署，不等于完整异常处理已经实现。

复现过程同时记录工具调用次数和会话轮次。Reference 组织依据实际任务提炼，开发期候选配置不得冒充已验证配方。

## 6. 后续设计讨论事项

- 确定首个测试场景的硬件、驱动、CANN、vLLM-Ascend / vLLM 版本、模型及镜像。
- 确定性能测试工具入口、负载配置、指标口径与结果判据。
- AISBench 运行位置作为环境配置记录，宿主机或容器均可，沿用手工验证方式，不作为阻塞项。
- 确定 `plan - test` 的阶段边界、询问提示词、交接 JSON、脚本职责及结构化输出。
- 确定单条推理冒烟请求与通过判据。
- 确定时延记录口径、强弱 Agent / Model 组合、复现次数和稳定性判据。
- 依据实际测试任务确定配置与 Reference 的组织形式。

## 2026-10-31：用户逐项核对后的最新方向（优先于此前冲突描述）

中心思想：以job_spec引导有人值守阶段的信息收集与初步验证，随后自动化上机执行。先让最小case顺利完成，再逐步加入简单恢复和有限重试。本轮先修订Skill及配套说明，不启动Agent测试或强弱模型复现。

1. 模型权重、镜像、测试case和测试工具是实际用户输入；主机、路径、设备、网络等来自收集与现场核验，不得写死为通用限制。提供填写提示词模板。
2. 根据真实任务评估job_spec信息是否充分、合理，再冻结字段并适配Schema与代码；不机械照搬全部设计字段。
3. 冒烟策略未指定时为default：一次最小curl真实推理请求。其他策略后续扩展，默认不强制KV分析或所有DP域覆盖。
4. 每个最小case开始前检查推理服务状态，结束后更新。服务仍有效且无需重部署时，跳过deploy/smoke。是否释放服务或容器由明确策略决定，不先要求完整复杂的资源释放框架。
5. 当前性能测试串行，并加入容器级独占锁。精度测试是否串行未确定，本版不实现并行。
6. job_spec表达最大重试次数，默认3（首次尝试外最多额外3次）；耗尽上报当前case失败，在服务和残留状态允许时处理下一case。故障分类和更复杂恢复以后扩展。
7. 六组共用服务、case间隔离前缀缓存、最后停止服务及容器，都是该实验的明确策略实例，不能升级成全局架构规则。

新Skill及其信息收集、job_spec评估、服务状态说明是本轮修订成果。旧Python执行器、旧Schema与DSV4示例尚待适配，现有手工基线不证明新架构已实现。完整Agent运行及强弱模型复现待Skill修订后另行推进。

## 2026-10-31 单 case 实现适配

本轮按用户确认从单 case 开发：65536 输入 tokens、1024 输出 tokens、并发 32、正式请求 64、目标前缀 50%、一轮。覆盖此前本轮建议中的 128 请求；历史六组基线参数保留为历史，不据此推导新请求数。

job_spec 升为 v2，每次只接受一个 case。通用执行器读取用户输入的镜像、权重、容器配置、工具与所选配方；DSV4 P/D 参数放配方，默认冒烟改为一次非流式 curl。状态文件记录实例身份、case 尝试及分层释放；容器锁覆盖阶段与 case 执行；测试有限重试默认 3 次，归属/残留不明立即上报。清理策略由 after_case 与 task_end 明确选择。

旧固定六组示例、重复迁移包、未使用适配器与旧资源登记/重试脚手架退出当前包，保留在本地忽略的归档。docs 继续仅放设计与工程计划。完整 Agent 与强弱模型复现仍不属于本轮范围。

## 2026-10-31 本地归档与代码仓库分离

用户要求本地归档不放在代码仓路径。本机日志、证据、报告、运行产物和旧代码归档统一迁至 `/path/to/benchmark-artifacts/logs/`，迁移逐文件核验 SHA256；旧记录中的仓库内 logs 路径仅保留为历史。代码仓库只保留实现、测试、配置示例与设计/工程计划。远端任务工作目录不变，推送不包含本地产物。

## 首次提问简化与新任务默认值

按用户本轮要求，首次模板不再要求正式请求数、AISBench路径或冷/热缓存术语；新任务默认正式请求数=并发×4，用户明确指定时覆盖。工具位置由 Agent 探测；每个 case 默认重置前缀缓存、预热、测试并释放客户端/临时链接。同部署配置复用有效服务，部署配置改变重新部署冒烟，任务结束停止本任务服务与容器。本轮更新会话模板与约定；工具入库、自动发现/传输和跨 case 编排仍待实现，历史64请求验证规格不变。

## 首次对话与内部 case 管理解耦

用户要求默认执行规则及通用能力边界不作为首次回复尾注。对外接受自然语言的服务器、部署形式及测试需求，Agent 提取并保存部署与 case 的对应关系，转为标准化内部 case；单 case 设计是执行/存储/扩展管理单元，不要求用户拆分或理解内部格式。仅询问实际缺项和影响范围的具体歧义；真实能力缺口在承诺执行前说明。本轮只调整 Skill 的对话和标准化指引，不宣称批量任务执行器已经实现。

## 2026-11-01：串行执行与现场绑定，配置存储只做埋点

- 用户自然语言输入由 Agent 规范化为部署和 case，原始本地/远程脚本路径不是 job_spec 的执行依赖。job_spec v3 存命令、环境与参数模板，现场路径与探测值独立绑定。
- plan_run 固定 case 顺序并生成入口；有人值守阶段 preflight 检查环境、动态发现工具、绑定 IP/网卡、规划端口和生成启动脚本；执行期逐 case 调用 deploy、evaluate、finalize。
- deploy 读取并核验服务状态，同部署连续 case 可复用；当前不同部署使用独立容器，切换时停止旧容器。缓存在下一 case 预热前实际重置；客户端、服务、容器按各自生命周期释放。
- 配置库、版本检索和自动选配暂不实现，只记录 task_normalized、bindings_resolved、deployment_verified、case_finished 事件。任务计划、状态、结果留档仍属执行必要产物。
- v2 配方保留作回归；新 v3 路径不依赖固定 recipe。真实新流程压测与模拟自动检查分开报告。

## 2026-11-01：开发阶段仅保留 v3

按用户最新要求删除 v2 Schema、示例、配方渲染器、P/D 模板及兼容分支；测试迁移到 v3。仍使用的 PD 代理及许可证移至 旧版代理资源目录。运行时 resolved-1 是 v3 预检产物，不是另一种用户输入格式；case 必须由串行循环显式传入，释放统一由 finalize 负责。此决定取代前文保留 v2 回归的约定。

## 2026-11-01：动态选择通信网卡

默认不填写 network_interface；上机发现 UP 且具备可用 IPv4 的通信接口，按当前协商速率选唯一最高者，不按 data0 名称或管理地址固定选择。sysfs 读取失败时使用 ethtool；排除 bridge/veth 等虚拟接口，保留 VLAN。速率缺失、并列或多个地址交回有人值守核验，允许明确核验后的接口覆盖。选择依据与候选记录进现场绑定结果。

## 2026-11-01：实例拓扑与串行子任务

按用户确认将 deployment 分为 model、runtime、instances、connections、endpoint。instances 按 node/container_group 归入容器，单机 PD 与双机 PD 共用同一拓扑模型。case 只保留负载定义，sub_tasks 引用部署与 case 并配置 after_case。实际服务器与路径仅在仓库外 bindings.nodes 保存；旧平铺输入不再兼容。

协调端调用固定节点脚本，节点保留已有归属核验、容器锁、进程登记和释放实现。模型进程先就绪再启动 proxy，整套服务完成入口冒烟后才可测试。当前只实现串行子任务与一个 P/一个 D/一个 proxy；phase 并行屏障、多 P/D 拓扑和复杂恢复不提前实现。多节点失败后停止后续子任务，逐节点收尾，释放失败独立报告。

## 2026-11-01：Agent 侧任务监控

按用户确认，后台启动核验、当前聊天监控绑定、事件通知去重及停止监控由 Agent 承担。默认每5分钟检查，正常静默，终态或需人工处理时上报；任务结果和分级清理证据共同决定最终结论。监控不执行重跑或自动修复。monitor-state.json 保存在仓库外，job_spec 和五阶段脚本不接入应用监控 ID。使用应用工具管理监控，能力不可用时明确告知；断连不等于失败，进程退出不等于成功。

## 2026-11-01：record_only 子任务异常策略

sub_tasks 显式展示 after_case，并新增 phase_id（默认 pp1，仅分组，仍串行）和 on_failure（当前仅 record_only）。子任务异常保留失败结果及阶段，不请求 Agent 修复；核验客户端清理和全部服务，健康则复用，确定退出则释放并核验后置 RELEASED，由下一 deploy 重建。UNKNOWN 或释放未核验阻塞，最终汇总仍反映失败。此决定取代之前任何子任务失败均停止后续任务的行为；监控对允许继续的 case 异常静默。

## 2026-11-01：任务级容器复用

本节取代按 deployment/container_group 隔离容器的旧策略。每台机器的首个任务容器以总 job_id 命名，兼容镜像和容器配置跨部署复用；预检汇总模型挂载和设备，不兼容时使用子编号容器。移除用户 placement.container_group 字段。切换部署默认 stop_service，不强制 stop_container；服务确认退出后也优先清理服务并复用容器。容器归属与服务摘要分离，共享登记控制当前服务身份。任务结束默认核验停止、删除全部本任务容器，保留宿主产物、镜像和权重。


## 2026-11-01：默认容器基线与显式覆盖

用户提供的docker run作为默认：root、host网络/PID、500g共享内存、privileged、八卡及管理设备和完整挂载。去除重复npu-smi挂载。默认清单集中维护，bindings.mounts按目标路径覆盖/追加；job_spec的runtime.container显式参数优先，默认值由plan_run补齐冻结。预检核验实际来源，不能让Docker创建空目录代替缺失配置文件。自动任务保留自身工作目录与sleep infinity加docker exec的服务管理方式。已冻结任务快照不原地更新。

## 2026-11-01：宿主机整组自动推进

用户确认：单机在本机宿主启动执行进程，多机在所选主节点宿主启动；任务完成按策略释放。新增外层整组进程，使用group-plan.json引用已完成预检的独立job_spec和任务包，自动推进依赖，不要求Agent在每个任务之间持续操作。

独立服务器上的单机任务可并行；共享服务器的后继须等待前置终止且全部节点释放核验通过。DONE表示已结束且释放通过，测量结果另行记录；前置测量失败但释放通过允许继续，整组仍反映失败。UNKNOWN保留资源占用并继续核验，BLOCKED阻塞相关后继。五阶段职责及每个job_spec内部串行不变，phase_id仍仅分组。仅支持已适配的部署，不因外层协调而新增3P1D支持。

## 2026-11-01：阶段事件、终端观察与低频通知

以subcase和case内阶段记录事件，包含doing/done/fail/skipped/blocked/retry与attempt。事件覆盖部署、冒烟、缓存重置、预热、正式请求、验证和分级释放。主节点汇集增量事件，原始记录保留UTC，终端显示北京时间到秒。

提交前给用户可复制的SSH观察命令，不自动打开窗口。关闭观察连接不影响后台任务。远端普通进程每30秒检查执行状态，不调用模型；Agent兜底改为默认每60分钟一次，整组只建一个监控，正常静默。此决定取代此前每5分钟的默认频率。低频监控不负责启动后继或修复，终态仍需结果及释放证据；应用不可用或通知投递未验证须明确说明。

主机重启后的自动恢复、复杂调度和自动配置优化仍不进入首版。当前整组真实SSH验证使用合成任务，不能作为模型性能测试或真实容器释放验收结论。
