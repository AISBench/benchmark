1. 项目概述

AISBench 是一个基于 OpenCompass 构建的大模型评测工具。它的核心功能是对各种大语言模型（LLM）进行精度评测和性能评测。


属性说明
语言Python 3.8+
版本3.1.0
开源协议Apache 2.0
命令行入口ais_bench → cli/main.py
核心依赖mmengine（配置系统）、torch、transformers、aiohttp、asyncio
模型后端vLLM、MindIE、Triton、TGI、SGLang、HuggingFace (local)
评测数据集40+ (GSM8K / MMLU / MMMU / HumanEval / SWE-Bench / VBench ...)
基座框架OpenCompass

两大评测场景

🔍 精度评测 (Accuracy)

验证模型在各类问答/推理基准数据集上的正确率。支持 40+ 数据集，涵盖文本、多模态、代码、Agent 等场景。

GSM8K MMLU HumanEval MMMU SWE-Bench BBH VBench C-Eval Math BFCL

⚡ 性能评测 (Performance)

测试模型服务的吞吐量、延迟、并发能力。支持压力测试、稳态性能测试、真实业务流量模拟。

吞吐量 延迟 并发 TTFT TPOT

3.2 核心概念：注册器模式 (Registry Pattern)

这是整个项目最重要的设计模式。在 registry.py 中定义了多个注册器：

注册器名称用途注册位置
PARTITIONERS任务分区器partitioners/
RUNNERS任务执行器runners/
TASKS任务类型tasks/
MODELS模型后端models/
LOAD_DATASET数据集加载器datasets/
ICL_INFERENCERS推理器openicl/icl_inferencer/
ICL_EVALUATORS评测器openicl/icl_evaluator/
ICL_RETRIEVERS样例检索器openicl/icl_retriever/
PERF_METRIC_CALCULATORS性能指标计算器calculators/
为什么要用注册器模式？
它让项目变得高度可扩展。新增一个数据集只需在 datasets/ 下新建一个文件，用 @LOAD_DATASET.register_module() 装饰器注册即可。不需要修改任何现有代码。

4. 程序执行流程

4.1 从命令行到结果输出的完整链路

Step 1: 启动

# 命令行示例
ais_bench --models qwen2_7b --datasets gsm8k --mode all

入口函数：main.py:main() → 创建 TaskManager 实例。

Step 2: 参数解析

ArgumentParser.parse_args() 解析命令行参数，包括：

参数说明示例值
--models要评测的模型qwen2_7b, llama3_8b
--datasets评测数据集gsm8k, mmlu, humaneval
--mode运行模式all / infer / eval / perf / viz
--max-num-workers最大并行数4
--work-dir输出目录outputs/default

Step 3: 配置加载

ConfigManager.load_config() 根据 --models 和 --datasets 参数，从 configs/ 目录搜索并加载对应的 Python 配置文件。配置文件定义了模型类型、数据集路径、推理方式、汇总方式等。

核心函数调用链：

_load_models_config()    → 加载模型配置（API地址/本地路径/推理参数）
_load_datasets_config()  → 加载数据集配置（数据路径/推理方式/评测方式）
_load_summarizers_config() → 加载汇总器配置（如何汇总结果）
_update_and_init_work_dir() → 创建工作目录 outputs/{timestamp}/

Step 4: 工作流执行

workers.py 定义了完整的工作流映射：

WORK_FLOW = {
    "all":   [Infer, JudgeInfer, Eval, AccViz],   # 全流程
    "infer": [Infer],                              # 仅推理
    "eval":  [JudgeInfer, Eval, AccViz],         # 仅评测（跳过推理）
    "viz":   [AccViz],                             # 仅可视化
    "perf":  [Infer, PerfViz],                    # 性能评测
}

每个 Worker 依次执行 update_cfg()（更新配置）→ do_work()（执行工作）。

4.2 精度评测流程 (mode=all)

1. Infer
推理阶段
→
2. JudgeInfer
裁判推理
→
3. Eval
评测阶段
→
4. AccViz
结果汇总

Infer 阶段 (推理)

  1. 分区：NaivePartitioner 将模型-数据集组合拆分成多个 Task
  2. 去重：clear_repeat_tasks() 去除重复的模型-数据集组合
  3. 合并：如果指定 --merge-ds，将同模型同数据集类型的任务合并
  4. 执行：LocalRunner 多进程+协程并发执行推理任务
  5. 输出：推理结果以 JSONL 格式保存到 predictions/ 目录

Eval 阶段 (评测)

  1. 读取推理阶段产出的 JSONL 预测文件
  2. 根据数据集类型调用对应的 Evaluator（如准确率计算、BLEU、Pass@k）
  3. 结果保存到 results/ 目录

AccViz 阶段 (汇总)

  1. 读取所有评测结果
  2. DefaultSummarizer 生成汇总表格/报告
  3. 输出到控制台并保存文件

4.3 性能评测流程 (mode=perf)

1. Infer
推理+计时
→
2. PerfViz
指标计算+可视化

性能评测关注的是服务性能而非答案正确率：

  • 吞吐量 (tokens/s)：每秒处理的 token 数量
  • TTFT (Time To First Token)：首 token 延迟
  • TPOT (Time Per Output Token)：每个输出 token 的平均时间
  • 延迟分布：P50/P90/P99 延迟
  • 支持压力测试 (--pressure) 和稳态测试

5. 核心模块深度解析

5.1 TaskManager — 总调度器

文件：ais_bench/benchmark/cli/task_manager.py

职责：程序的总入口，负责串联参数解析、配置加载、工作流执行。

class TaskManager:
    def __init__(self):
        self.args_parser = ArgumentParser()       # 1. 解析参数
        self.args = self.args_parser.parse_args()
        self.config_manager = ConfigManager(...)   # 2. 加载配置

    def run(self):
        # 3. 根据 mode 选择工作流
        self.workflow = [worker_class(self.args)
                         for worker_class in WORK_FLOW.get(run_mode)]
        # 4. 加载并更新配置
        cfg = self.config_manager.load_config(self.workflow)
        # 5. 执行工作流
        WorkFlowExecutor(cfg, self.workflow).execute()

5.2 Workers — 工作流节点

文件：ais_bench/benchmark/cli/workers.py

职责：定义评测流水线的每个阶段。每个 Worker 都是一个策略模式的实现。

Workerupdate_cfg() 做什么do_work() 做什么
Infer 配置推理的 partitioner + runner + task 类型 创建 Partitioner 分区任务 → 创建 Runner 执行任务
JudgeInfer 配置裁判模型推理（用于主观评测） 同 Infer，但使用裁判模型对结果进行二次推理
Eval 配置评测的 partitioner + runner + task 类型 读取预测结果 → 计算评测指标（准确率/BLEU/Pass@k）
AccViz 配置汇总器类型 收集所有评测结果 → 生成汇总报告
PerfViz 配置性能汇总器 + 指标计算器 计算性能指标（吞吐/延迟）→ 生成可视化报告

5.3 OpenICL — In-Context Learning 框架

目录：ais_bench/benchmark/openicl/

这是项目中最核心的技术模块，实现了完整的 In-Context Learning 流程：

Retriever
检索 Few-shot 样例
→
PromptTemplate
组装 Prompt
→
Inferencer
调用模型推理
→

评测结果

组件职责举例
ICL_RETRIEVERS 从数据集中选取 Few-shot 样例 随机选取、按相似度检索
ICL_PROMPT_TEMPLATES 定义 Prompt 模板格式 Chat 格式、字符串格式、CoT 格式

5.5 并发架构：多进程 + 协程

这是 AISBench 支持 30,000+ 并发的核心技术方案。性能评测和 API 推理都采用了这套架构：

┌─────────────────────────────────────────────────────────────────┐
│                      主进程 (Main Process)                   │
│                                                                 │
│  1. 序列化数据集 → pickle.dumps() → 写入共享内存 (Shared Memory)  │
│  2. 创建 Token 桶 (BoundedSemaphore) 用于速率控制                 │
│  3. 创建消息共享内存 (Message Shared Memory) 用于任务间通信        │
│  4. 启动 N 个 Worker 子进程                                      │
└──────────┬──────────────────────────┬───────────────────────────┘
           │                          │
    ┌──────▼──────┐            ┌──────▼──────┐
    │ Worker 进程 1│   ...      │ Worker 进程 N│   (最多 cpu_count × 0.8)
    └──────┬──────┘            └──────┬──────┘
           │                          │
    ┌──────▼──────────────────────────▼──────┐
    │  每个 Worker 进程内部：                   │
    │                                         │
    │  Producer Thread (生产者线程)             │
    │    │ 从共享内存读取序列化的样本             │
    │    │ 反序列化 → 放入 Janus Queue          │
    │    ▼                                     │
    │  Async Event Loop (异步事件循环)           │
    │    │ asyncio + aiohttp                  │
    │    │ 每个进程最多 500 个并发协程            │
    │    │ 通过 Token 桶实现速率控制              │
    │    ▼                                     │
    │  HTTP 请求 → API 模型服务                  │
    │    │ (vLLM / MindIE / Triton / TGI / SGLang) │
    │    ▼                                     │
    │  结果写回共享内存 → 主进程汇总              │
    └──────────────────────────────────────────┘

关键技术点

技术作用
multiprocessing.shared_memory进程间零拷贝数据共享，避免大数据序列化开销
asyncio + aiohttp单进程内支持 500 并发 HTTP 请求
multiprocessing.BoundedSemaphoreToken 桶算法，控制请求发送速率
Producer-Consumer 模式生产者线程 + Janus Queue 解耦数据读取和请求发送
3 种请求调度方式固定速率、泊松到达、时间戳 Trace 回放

6. 设计模式 & 编程技巧

🔌 注册器模式 (Registry Pattern)

项目通过 mmengine.Registry 实现了完整的注册器模式。每个模块通过装饰器注册，运行时通过配置中的 type 字段动态构建实例。

# 定义注册器
TASKS = Registry('task', locations=get_locations('tasks'))

# 注册一个任务
@TASKS.register_module()
class OpenICLEvalTask(BaseTask):
    ...

# 通过配置构建实例
task = TASKS.build(dict(type='OpenICLEvalTask'))

🔄 策略模式 (Strategy Pattern)

Workers 层使用了策略模式。通过 WORK_FLOW 字典定义不同 mode 下的 Worker 组合，运行时动态选择执行策略。

📋 模板方法模式 (Template Method)

BaseWorker 定义了 update_cfg() + do_work() 两个抽象方法，子类实现具体逻辑。执行顺序由框架控制。

🏭 延迟导入 (Lazy Import)

在 task_manager.py 中，ConfigManager 的导入被延迟到参数解析之后：

def __init__(self):
    self.args = self.args_parser.parse_args()
    # 延迟导入，加速 "ais_bench -h" 的响应速度
    from ais_bench.benchmark.cli.config_manager import ConfigManager
    self.config_manager = ConfigManager(self.args)
为什么要延迟导入？ 因为 ConfigManager 依赖很多重型库（torch、transformers 等）。如果用户在命令行只是输入 ais_bench -h 查看帮助，延迟导入可以避免加载这些重型库，让帮助信息秒出。

📦 配置驱动 (Config-Driven)

整个项目的核心设计哲学。用户通过 Python 配置文件定义评测的方方面面：

from mmengine.config import read_base

with read_base():
    from ...gsm8k_gen_0_shot_cot_str import gsm8k_datasets
    from ...vllm_api_general import models

datasets = gsm8k_datasets    # 数据集配置
models = [...]                # 模型配置
work_dir = 'outputs/demo/'    # 输出目录

--mode执行流程适用场景
allInfer → JudgeInfer → Eval → AccViz完整精度评测（默认）
inferInfer仅推理，不评测
evalJudgeInfer → Eval → AccViz仅评测已有推理结果
vizAccViz仅汇总已有评测结果
perfInfer → PerfViz性能评测（吞吐/延迟）
perf_vizPerfViz仅可视化已有性能数据
judgeJudgeInfer仅运行裁判模型推理
infer_judgeInfer → JudgeInfer推理 + 裁判推理

8. 给初学者的学习建议

📖 按这个顺序阅读代码

  1. 第一步：读懂 cli/main.py（只有 9 行！理解入口）
  2. 第二步：读懂 cli/task_manager.py（理解总调度逻辑）
  3. 第三步：读懂 cli/workers.py（理解工作流机制）
  4. 第四步：读懂 registry.py（理解注册器模式）
  5. 第五步：选一个数据集配置（如 configs/datasets/gsm8k/）理解配置格式
  6. 第六步：读 tasks/openicl_infer.py 理解推理任务如何执行
  7. 第七步：读 models/api_models/ 理解模型如何被调用
  8. 第八步：读 openicl/ 理解 ICL 框架的核心抽象

💡 关键概念理解清单

概念一句话解释
Registry（注册器）一个"班级花名册"，通过名字就能找到对应的类
Config（配置）一个嵌套字典，用 Python 文件描述评测的方方面面
Partitioner（分区器）把一个大任务切成多个小任务，分配给不同 GPU/进程
Runner（执行器）真正"干活"的人，负责任务的并行执行
Worker（工作者）流水线上的一个"工位"，如推理工位、评测工位
Inferencer（推理器）封装了"如何调用模型"的逻辑
Evaluator（评测器）封装了"如何打分"的逻辑
ICL（上下文学习）通过给模型看几个例子（Few-shot），让模型学会回答问题
