# Service Performance Testing in Multi-Level Concurrency Scenarios

## I. Introduction

Multi-level concurrency is a common multi-task combined performance stress-testing scenario. It aims to find the model's performance bottleneck by analyzing performance test results at different concurrency levels.

This document provides command-line usage examples supported by AISBench. Specifically, a single command expands the concurrency levels (`--batch-size`) and request counts (`--num-prompts`) into multiple tasks, and after completion aggregates them into CSV and HTML reports for comparing throughput and latency across concurrency levels:

- **Throughput dimension**: whether request throughput and output token throughput still grow as concurrency increases
- **Latency dimension**: how fast the Average and P99 of E2EL, TTFT, TPOT, and ITL degrade as concurrency increases
- **Bottleneck identification**: the concurrency level where throughput reaches a plateau while P99 latency starts to rise steeply is the performance inflection point under this service configuration


## II. Quick Start

### 2.1 Command Example

Prerequisites:

1. Service deployment is complete, and the model id returned by `/v1/models` matches the `model` field in the model configuration
2. A random synthetic dataset is used; for dataset configuration, see the [Guide to Using Random Synthetic Datasets](synthetic_dataset.md)

Example:

```bash
ais_bench \
  --models vllm_api_stream_chat \            # Use the streaming chat model
  --datasets synthetic_gen_tokenid \         # Use the random token id dataset
  --mode perf \                              # Performance testing scenario
  --tokenid-config-request-size 8192 \       # Number of tokens per request (input length)
  --tokenid-config-prefix-len 0 \            # Number of shared prefix tokens per request (prefix length)
  --batch-size 1 8 \                         # Maximum concurrency for sending requests
  --num-prompts 1 8 \                        # Total number of requests to send
  --request-count 8 \                        # Total number of requests generated by the random synthetic dataset (no fewer than the total number of requests to send)
  --path /mnt/weight/Qwen3.8-27B-w8a8 \      # Path to the tokenizer/model vocabulary files
  --model-name qwen3.8 \                     # Name of the model loaded on the server
  --max-out-len 1024 \                       # Maximum number of output tokens (output length) of the inference service
  --num-warmups 16 \                         # Number of warmup requests before sending formal requests
  --generation-kwargs '{"ignore_eos":true}'  # Ignore eos in the inference service output
```

Notes:

- When multiple `--batch-size` values are passed, the command expands into one concurrency level per value; `--num-prompts` must contain the same number of values and is paired one-to-one by position
- Each concurrency level becomes an independent task, and the model `abbr` is automatically suffixed with `-bs{N}` (for example, `vllm_api_stream_chat-bs8`), so output files do not overwrite each other
- `--request-count` sets the total number of requests generated for each level; if `--num-prompts` is not specified, the actual number of requests sent equals `--request-count`
- Tasks run serially by default with a 5s cooldown between consecutive tasks, preventing queued requests from the previous level from contaminating the results of the next level

For an example covering multiple input/output lengths plus multiple concurrency levels, see [aisbench_vllm_performance_zh_cn.sh](../../../ais_bench/configs/performance_benchmark/aisbench_vllm_performance_zh_cn.sh).

**Artifact Structure**

```
outputs/default/20251102_103326/
├── combos_manifest.json          # Snapshot of combination parameters (mapping between concurrency levels and request counts)
├── batch_perf_summary.csv        # Aggregated metrics of all combinations (pivotable/sortable)
├── batch_perf_report.html        # Visualization report of all combinations (single file, can be opened offline)
├── performances/
│   ├── vllm_api_stream_chat-bs1/
│   │   ├── synthetic.csv         # Metric statistics of a single task
│   │   ├── synthetic.json        # Common metrics of a single task
│   │   ├── synthetic_details.jsonl  # Per-request details
│   │   └── synthetic.html        # Report of a single task
│   └── vllm_api_stream_chat-bs8/
└── logs/infer/                   # Execution logs of each task
```

**Summary Report**

`batch_perf_report.html` is organized into the following sections, and supports Chinese/English switching and light/dark themes:

| Section | Content |
| --- | --- |
| Report Overview | Run summary, all-task metric comparison wide table, best-performing configuration, conclusions and recommendations |
| Metric Statistics | Metric statistics table for each task (identical to the content of `synthetic.csv`) |
| Percentile Curves | Percentile curves of E2EL, TTFT/TPOT/ITL, input/output token counts, and token throughput |
| Latency Analysis | Curves of latency, TTFT, and TPOT as concurrency changes |
| Throughput Analysis | Curves of request throughput, token throughput, and success rate as concurrency changes |
| Per-Task Details | Run summary, metric statistics table, and per-request detail curves for each task |
| Definitions and Notes | Metric definitions, missing-data notes, and runtime warnings |

💡 For the meaning of specific performance parameters, refer to 📚 [Explanation of Performance Evaluation Results](../base_tutorials/results_intro/performance_metric.md).

## III. Notes

1. **Requests no fewer than the concurrency level**: when a level's `--batch-size` is greater than the number of requests actually sent at that level, the real concurrency is limited by the request count; the command line emits a concurrency-window warning, and the observed values in the report do not represent the target concurrency of that level

2. **Pre-start validation**: `--batch-size` and `--num-prompts` must correspond one-to-one; if the numbers of values on the two sides differ (for example, multiple `--batch-size` values but only one `--num-prompts` value), the command exits with an error before startup and no partial tasks are created

3. **No latency breakdown in non-streaming mode**: with `--no-stream`, TTFT and per-token latency cannot be measured; the corresponding statistics are left empty in the summary CSV, and the related curves are not drawn in the report

4. **No summary for a single level**: when only one `--batch-size` is passed, the single-task flow is used, and neither `combos_manifest.json` nor the summary report is generated

5. **Failure isolation**: a failed level does not affect the execution of subsequent levels; failed levels are marked `fail` in the CSV, while other levels are summarized normally
